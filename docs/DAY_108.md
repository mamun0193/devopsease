# Day 108 — Custom Domain & TLS Certificate Management Platform 🌐🔐

## Executive Summary
On Day 108, DevOpsEase evolved from an internal application runner into a comprehensive Platform-as-a-Service (PaaS). We architected and deployed the frontend **Custom Domain and Certificate Management Platform**. This release empowers users to map bespoke domain names (e.g., `api.devopsease.com`) to their internal applications, complete with zero-touch TLS certificate provisioning, strict DNS ownership verification, and highly granular audit logging.

This document serves as an exhaustive technical breakdown of the React components, state management, API integrations, and the architectural troubleshooting that took place during this sprint.

---

## 1. Technical Implementation: Domain Registry (`DomainsPage.tsx`)

The `DomainsPage` acts as the command center for all public-facing routing configurations within a workspace.

### 1.1 State Management & Data Fetching
The page relies on a robust React state machine to handle asynchronous data and pagination:
*   **Domain Pagination**: Managed via `page` and `pagination` state objects. The UI fetches data using `domainsApi.listDomains({ page, limit: 20 })`, ensuring scalability for workspaces with hundreds of domains.
*   **Application Pre-fetching**: On initial mount, `fetchApps()` queries the `applicationsApi` to retrieve all active applications. This data is critical for populating the "Target Application" dropdown during domain registration.

### 1.2 Domain Registration Flow (The Modal)
When a user initiates the "Add Custom Domain" flow, they are presented with a strictly validated form:
*   **Hostname Input**: Captures the Fully Qualified Domain Name (FQDN).
*   **Target Application**: A critical `<select>` dropdown populated by the pre-fetched `applications` array. The user **must** bind the domain to an internal application ID (`appId`).
*   **Payload Submission**: The form submission invokes `domainsApi.addDomain({ hostname, applicationId, type: 'custom' })`. Upon success, the modal closes, fields reset, and the domain list hard-refreshes.

### 1.3 Data Grid & Dynamic Badging
The primary UI is a responsive data table. A dedicated `StatusBadge` component maps backend domain states to specific Tailwind CSS classes for immediate visual feedback:
*   `connected` / `healthy` ➔ Emerald Green (`bg-emerald-500/10 text-emerald-500`)
*   `verified` ➔ Blue (`bg-blue-500/10 text-blue-500`)
*   `pending_verification` ➔ Amber (`bg-amber-500/10 text-amber-500`)
*   `verification_failed` / `unhealthy` ➔ Red (`bg-red-500/10 text-red-500`)

## 2. Technical Implementation: Domain Lifecycle & Diagnostics (`DomainDetailPage.tsx`)

The `DomainDetailPage` is a dense, diagnostic dashboard for a single domain entity.

### 2.1 Parallel Data Hydration
To minimize layout shift and loading times, `fetchData()` performs concurrent requests using `Promise.all`:
```typescript
const [domainData, eventsRes, certsRes] = await Promise.all([
    domainsApi.getDomain(id!),
    domainsApi.getDomainEvents(id!, { limit: 10 }),
    domainsApi.getCertificateHistory(id!)
]);
```
Once the primary domain data resolves, a secondary `try/catch` block isolates the fetching of the linked target application using `applicationsApi.getApplication(appId)`.

### 2.2 DNS Verification Engine
To prevent domain hijacking, DevOpsEase enforces a strict DNS challenge workflow.
*   **Conditional Rendering**: If `domain.status === 'pending_verification'`, an Amber alert box appears.
*   **The Challenge**: The UI extracts `domain.verification.token` and displays the exact `TXT` record (`_devopsease-challenge`) the user must append to their registrar.
*   **User Experience**: Features integrated `navigator.clipboard.writeText()` functions for one-click copying and a manual "Verify Now" button bound to `domainsApi.verifyDomain(id)`.

### 2.3 Zero-Touch TLS Module
The TLS Certificate section dynamically adapts based on the `activeCertificate` sub-document:
*   **Installed**: Renders an Emerald `ShieldCheck` icon, displaying the issuance date, expiration date (formatted via `date-fns`), and confirms auto-renewal is active.
*   **Expired/Failed**: Renders a Red `ShieldAlert` icon, providing emergency action buttons triggering `domainsApi.renewCertificate()`.
*   **Processing**: Renders a spinning `RefreshCw` icon while the backend negotiates the Let's Encrypt ACME challenge.

### 2.4 The "Target Application" Context Sidebar
To provide holistic context, the sidebar maps the external domain back to the internal infrastructure. Using the data fetched from `applicationsApi`, it renders:
*   The application's `name` and `slug`.
*   A `Server` icon (via `lucide-react`).
*   The application's real-time `status` (e.g., `running`, `stopped`), colored Emerald if healthy.

### 2.5 Audit Log / Explainability Timeline
PaaS environments require absolute transparency. The UI constructs a chronological timeline of `DomainEvent` documents.
*   **Visual Routing**: Success events (e.g., `VERIFICATION_PASSED`) receive a `CheckCircle2`, while failures receive an `AlertCircle`.
*   **Metadata**: It exposes *who* triggered the event (`actor`), *how* it was triggered (`trigger`), and the backend's *justification* (`reason`), severely reducing support overhead for DNS misconfigurations.

## 3. API Client Architecture (`domainsApi.ts` & `applicationsApi.ts`)

The frontend relies on two highly structured Axios clients exposing strict TypeScript interfaces.

### 3.1 Domain Interfaces
```typescript
export interface Domain {
  _id: string;
  hostname: string;
  status: string;
  applicationId: any;
  verification?: { method: string; token: string; lastError: string | null; };
  activeCertificate?: { certificateId: string; expiresAt: string; status: string; };
  healthStatus: string | null;
}
```

### 3.2 Endpoint Mapping
The `domainsApi` encapsulates complex RESTful operations:
*   `addDomain`: `POST /domains`
*   `verifyDomain`: `POST /domains/:id/verify`
*   `retryVerification`: `POST /domains/:id/retry-verification`
*   `getDomainEvents`: `GET /domains/:id/events`

## 4. Technical Retrospective: The `applicationsApi` Incident

During the sprint, a critical architectural decision was debated, tested, and ultimately reversed regarding the `applicationsApi`.

### 4.1 The Anomaly
A frontend compilation error was thrown: `Cannot find module '../api/applicationsApi'`. Initial investigation revealed the file was untracked in Git. Assuming the file was deprecated legacy code, a decision was made to aggressively excise it.

### 4.2 The Excision
We stripped all references to `applicationsApi` from `DomainsPage.tsx` and `DomainDetailPage.tsx`.
*   Removed the "Target Application" `<select>` dropdown.
*   Removed the `applicationId` requirement from the `addDomain` payload.
*   Removed the Sidebar diagnostic panel from the details page.

### 4.3 The Architectural Reality & Restoration
Upon principal review, it became evident that **a PaaS domain without a mapped workload is architecturally invalid**. The Gateway reverse-proxy requires the `applicationId` to route incoming external traffic to the correct internal Docker container.

**The Fix:**
1.  **File Reconstruction**: We completely rebuilt `applicationsApi.ts` with its core CRUD methods (`getApplications`, `getApplication`).
2.  **Payload Restoration**: We reinstated `applicationId` as a mandatory field in `domainsApi.addDomain()`.
3.  **UI Reintegration**: We restored the state machines, `useEffect` pre-fetching, the dropdown modal, and the diagnostic sidebar in both React components.

This incident served as a stark reminder of the tight coupling between edge-routing (Domains) and internal compute (Applications) in modern cloud platforms.
