# Day 107: Preview Environment Platform Refactoring & Finalization

## Overview
On Day 107, the **Preview Environment Platform** subsystem underwent a comprehensive Principal Engineering architecture review. The goal was to transition the initial implementation from a functional prototype into a production-grade, highly scalable subsystem. 

The review surfaced key areas of improvement including over-engineered data models, IDOR security vulnerabilities, distributed scaling limits, and asynchronous race conditions. This document details the specific architectural changes and technical debt resolutions applied to stabilize the platform.

---

## 1. Architectural Simplification (Manifest Eradication)

### The Problem
The initial design introduced a `PreviewManifest` model alongside the `Preview` model. This was redundant because a `Preview` is inherently tied 1:1 to its provenance data (branch, commit, build) and the broader DevOpsEase platform already utilizes `BuildManifest` and `ReleaseManifest`.

### The Solution
*   **Flattened the Model**: We deleted the `previewManifest.model.js` completely.
*   **Embedded Documents**: The source provenance data was embedded directly into the `Preview` model under a `manifest` object.
*   **Impact**: This reduced the number of MongoDB collections, eliminated the need to `populate()` manifests on every API call, and aligned the architecture with the single-responsibility principle.

```javascript
// preview.model.js
manifest: {
    branch: { type: String, required: true },
    commitSha: { type: String, required: true },
    prNumber: { type: Number, default: null },
    trigger: { type: String, default: 'API' },
    buildId: { type: mongoose.Schema.Types.ObjectId, ref: 'Build', required: true },
    // ...other limits and configuration
}
```

## 2. Security Enhancements

### The Problem
Two severe vulnerabilities were discovered during the security review:
1.  **Insecure Direct Object Reference (IDOR)**: The `extendPreview` and `destroyPreview` endpoints blindly accepted any valid preview ID and executed the action without verifying if the requesting user actually owned the Preview or the underlying Repository.
2.  **Predictable URLs**: The preview slug generator used a 3-byte cryptographic hash, which provided only ~16 million permutations, making active environments vulnerable to enumeration attacks.

### The Solution
*   **Ownership Boundaries**: Added strict authorization checks to the `preview.service.js`. An action is now rejected with a `403 Forbidden` if the `userId` does not match the preview owner or the repository owner.
*   **Slug Hardening**: Upgraded the random slug generator to use a 4-byte hash (`crypto.randomBytes(4).toString('hex')`), exponentially increasing the entropy and preventing URL guessing.

## 3. Concurrency & Race Condition Resolution

### The Problem
The deployment orchestrator suffered from a race condition that could lead to orphaned "zombie" Docker containers. 
If a user triggered a manual preview destruction *while* the backend was actively provisioning the container (`deployFromBuild`), the destruction logic would clean up the database but the async deployment would continue running in the background. Once finished, the orchestrator would save the container details, map the URL, and forcefully revert the preview status back to `ready`.

### The Solution
*   **Post-Deployment Verification**: We injected a strict intercept check inside `_deployPreviewTarget`. Immediately after `deployFromBuild` resolves, the service re-fetches the current state of the Preview.
*   **Abort & Collect**: If the status transitioned to `destroying` or `destroyed` during the allocation window, the service intentionally aborts, instantly releases the newly created container via `removeDeployment`, and logs a `DEPLOYMENT_ABORTED` event.

```javascript
// Post-deployment check in preview.service.js
const currentPreview = await Preview.findById(preview._id);
if (!currentPreview || currentPreview.status === 'destroyed' || currentPreview.status === 'destroying') {
    await removeDeployment(deployment._id);
    logger.warn(`Aborted preview deployment for ${preview._id}: Preview was destroyed during deployment.`);
    return;
}
```

## 4. Distributed Scheduler Stability

### The Problem
The `PlatformScheduler` managed preview TTL expirations using standard Node.js `setInterval` polling. In a scaled PaaS environment running multiple Node instances, every node would concurrently attempt to expire and destroy the same preview environment.

### The Solution
*   **Atomic State Locking**: We refactored `runExpiryJob` to leverage MongoDB's `findOneAndUpdate` atomic operations instead of simple `find()` queries. 
*   **Claiming Work**: The query mandates `status: { $in: ['ready', 'failed'] }` and simultaneously updates the status to `destroying` in a single atomic transaction. This guarantees that only one cluster node can successfully claim the teardown job.

```javascript
// Atomic locking in PlatformScheduler
const lockedPreview = await Preview.findOneAndUpdate(
    { _id: preview._id, status: { $in: ['ready', 'failed'] } },
    { status: 'destroying' },
    { new: true }
);

if (lockedPreview) {
    // Proceed with safe destruction
}
```

## 5. Technical Debt and Syntax Fixes

During validation testing, several edge-case bugs and warnings were squashed:
*   **Mongoose Duplicate Indexes**: Resolved multiple strict index conflict warnings. Mongoose automatically generates indexes for fields marked `unique: true`, which caused conflicts with our explicit `schema.index()` declarations for fields like `applicationId`, `repositoryId`, and `userId`.
*   **Nested Field Types**: Adjusted `relatedResource` within the `PreviewEvent` schema. We originally attempted to declare a nested property literally named `type`, which Mongoose 6+ interprets as an invalid schema definition. Replaced this with `mongoose.Schema.Types.Mixed` to natively accept flexible payloads.
*   **Module Import Errors**: Fixed a destructive server crash caused by improperly destructuring an ES module default export (`authMiddleware`).

## Conclusion
The Preview Environment subsystem is now fully stable, highly scalable, and structurally coherent with the greater DevOpsEase application orchestration lifecycle. It acts as a natural, seamless extension of the deployment architecture rather than an isolated, divergent microservice.
